# 🧭 مخطط تعامل الوكلاء والتنسيق المؤسسي (Agent Orchestration & Coordination)
## التوثيق الهندسي الشامل — مشروع تخرج AI-COS Pharmacy (BIS)
### *كيف يتنسق 9 وكلاء ذكيون؟ — الجواب المعماري الصادق، المطبق في الكود*

---

## 1. السؤال الفخ — ولماذا يحتاج مخططًا صادقًا؟

أول سؤال متوقع في المناقشة بعد عرض الوكلاء التسعة:

> **"طيب الوكلاء بيتعاملوا مع بعض إزاي؟ مين بيقول للمخزون يكلم التسويق؟"**

هذا سؤال فخ لسببين:
1. أي مخطط يوحي بأن الوكلاء "يتسلسلون" أو "يتحدثون مباشرة" = وعد لا يستطيع الكود الوفاء به.
2. أي مخطط يخلط بين ثلاثة أنواع حوكمة مختلفة المواقع (صلاحيات الدخول / حواجز الوكيل / تدقيق ما بعد الإجراء) ينهار تحت أول سؤال دقيق.

لذلك: هذا الملف يوثق **الآليات الثلاث الحقيقية** كما هي في الكود، بالمخططين الرسميين.

---

## 2. الحقيقة المعمارية: الوكلاء لا يتحدثون مع بعضهم — يتنسقون عبر ثلاث آليات

### الآلية 1: التوجيه (Supervisor = Planner اختياري)
* المشرف يستقبل الاستفسار الحر، يحلل النية، ويخرج **خطة** (أي وكلاء وبأي ترتيب).
* **لا ينفّذ** — لا يستدعي أي وكيل داخل نفس الطلب.
* **الوصول المباشر متاح**: كل وكيل له Endpoint وكارت مستقل؛ الحدث التجاري يصل مباشرة.
* **الدليل**: `orchestrator.route_query()` يعيد `workflow_chain` (خطة)، ولا يستدعي أي خدمة وكيل.

### الآلية 2: التنسيق عبر البيانات المشتركة (Data-Mediated Coordination)
* **هذا هو "التعاون" الحقيقي بين الوكلاء** — لا رسائل مباشرة بينهم:
  * نموذج XGBoost يكتب `churn_probability` و`predicted_days` في `pending_reminders`
  * → محرك الاستهداف يقرأها ويصنف العملاء (Lead Scoring)
  * → وكيل التسويق والتسعير يتخذان قرارهما عليها
  * → النتائج تُكتب في الجداول نفسها → وكيل التحليلات يبني BSC منها
* **الفائدة المعمارية:** فصل كامل (Decoupling) — إضافة الوكيل العاشر لا تلمس التسعة؛ إيقاف أي وكيل لا يوقف البقية.

### الآلية 3: الرقابة الشاملة (Oversight Layer)
* كل إجراء من أي وكيل → `audit_logs`
* عامل WORM يلحق كل حدث في **دفتر خارجي متسلسل** (SHA-256، كل 300 ثانية)
* **المفتش الرقابي** هو الوحيد الذي "يرى الجميع" — ويقرؤهم عبر السجلات لا بمكالمات
* + عامل إعادة محاولة الأتمتة + تيليمتري التسليم (`automation_runs`)

## 3. المخططان الرسميان

### المخطط أ: خط أنابيب الوكيل الواحد (يتكرر ×9 — نفس البنية حرفيًا)

```text
① ENTRY AUTH ── RBAC (admin/customer) أو X-Internal-Token (M2M)
        ↓
② DATA ── PostgreSQL حية (بسياق المستأجر — RLS)
        ↓
③ DETERMINISTIC ENGINE ── محرك قطعي (Burn/EOQ/CLV/تصنيف)
        ↓
④ GUARDRAILS ── سقوف قسرية + حاجز سريري + بوابة جدوى   ◄ الحوكمة داخل الوكيل
        ↓
⑤ LLM ARTICULATION ── صياغة ضمن الحدود (fallback قطعي عند الفشل)
        ↓
⑥ ACTION + AUDIT ── إجراء + audit_logs
```

### المخطط ب: طبقة الحوكمة والمراقبة المحيطة (Surrounding Layer)

```text
┌────────────── GOVERNANCE & OBSERVABILITY — تحيط بالمنظومة كلها ──────────────┐
│  audit_logs (كل إجراء من أي وكيل)                                            │
│      ↓                                                                        │
│  WORM Ledger (دفتر خارجي append-only) ──► Compliance Inspector               │
│      ↓                                                                        │
│  Metrics (automation_runs + trial balance + BSC) ──► لوحات الإدارة            │
│  Evaluation Harness (حقيبة تقييم + سيناريو فشل متعمد)                         │
└───────────────────────────────────────────────────────────────────────────────┘
```

**لماذا "تحيط" وليست "خطوة"؟** لأن الرقابة ليست محطة يمر عبرها الإجراء فقط —
هي طبقة مستمرة: **تُلحق** (audit)، **تتحقق** (chain verify)، **تقيس** (metrics)،
**وقد تفشل وتصرخ** (NEEDS_ATTENTION تحت التلاعب — مثبت بـ failure_demo).

## 6. القيمة المعمارية (BIS)

* **Decoupling:** الوكلاء مستقلون — إضافة العاشر لا تلمس التسعة (تم فعليًا: customer_success أُضيف لاحقًا بلا لمس أحد).
* **Observability:** طبقة رقابة تحيط لا تتدخل — الفصل بين التنفيذ والرقابة (SoD معماري).
* **Fail-safe:** انهيار أي مكون (LLM/n8n/DB) لا يوقف البقية — تدهور رشيق موثق.
* **Honest Diagrams:** كل مخطط في المشروع قابل للتحقق ضد الكود — وهذا نادر في مشاريع التخرج.
