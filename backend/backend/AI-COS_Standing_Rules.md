AI-COS Pharmacy — قواعد المشروع الثابتة (Standing Rules)

الغرض: هذا المستند مرجع دائم لكل القرارات المعمارية المتفق عليها. اقرأه قبل أي مهمة جديدة، والتزم به دون الحاجة للسؤال عن كل نقطة فيه مرة أخرى. إذا واجهت قرارًا غير مغطى هنا وله أثر معماري حقيقي (تعديل Schema، تغيير مبدأ أمني، إضافة تقنية جديدة)، دوّنه في قسم "أسئلة مفتوحة" في نهاية تقريرك بدل ما تفترض حلاً بنفسك وتكمل. أي قرار صغير/تنفيذي عادي (تسمية متغير، ترتيب استيراد، تفاصيل تنفيذية داخلية) اتخذه بنفسك مباشرة دون سؤال.

1. المعمارية العامة
Backend: FastAPI + SQLAlchemy 2 (Async) + Alembic + Supabase (PostgreSQL + pgvector).
هيكل كل Domain: router.py (HTTP فقط) → service.py (منطق العمل) → schemas.py (Pydantic). الـ router لا يحتوي استعلامات قاعدة بيانات مباشرة أبدًا.
كل Domain مستقل بمسؤولية واحدة واضحة. لو دومين بدأ يحتوي منطقًا مالوش علاقة مباشرة بمسؤوليته الأساسية (مثال: منطق تحليلي جوه order)، أنشئ Domain جديد منفصل بدل التوسع العشوائي داخل الموجود.

2. قاعدة البيانات
مصدر الحقيقة الوحيد لأي Schema هو app/models/. أي تعديل على موديل موجود لازم Migration منفصلة موثقة (لا تعدّل migration قديمة بعد ما تكون نجحت فعليًا على Supabase).
أي عملية Upsert (إدراج أو تحديث حسب الحاجة) تُنفَّذ عبر insert(...).on_conflict_do_update(...) الخاصة بـ PostgreSQL، وليس منطق يدوي (SELECT ثم قرار).
أي فلترة بالـ Sort/Order تقبل قيمًا محدودة فقط (Literal أو Enum)، ولا تُمرَّر مباشرة كنص حر في الاستعلام (خطر SQL Injection).

3. الأمان والمصادقة
Supabase Auth هو المصدر الوحيد للهوية. لا نخزن باسورد ولا نصدر JWT بأنفسنا إطلاقًا، محليًا أو عبر أي مزود OAuth (بما فيه Google — يُفعَّل من Supabase Dashboard كـ Provider، وليس عبر كود FastAPI مخصص).
get_current_user (في app/dependencies/auth.py) يتحقق فقط من توقيع JWT الصادر من Supabase، ويربطه بجدول customers عبر auth_user_id.
أي Endpoint حساس (بيانات عميل، طلبات) يستخدم get_current_customer_tenant_scoped لضمان عزل tenant تلقائي — لا تسمح لأي استعلام بالوصول لبيانات خارج tenant المستخدم الحالي.
عند وصول مستخدم غير مصرَّح له لمورد يخص مستخدمًا آخر: أرجع 404 (Not Found) وليس 403 (Forbidden) — مبدأ عدم تسريب معلومة الوجود.
أي بيانات مالية (السعر مثلًا) تُحسَب دائمًا من قاعدة البيانات وقت التنفيذ، ولا تُقبَل أبدًا من الـ Request مباشرة (حتى لو العميل بعتها، تجاهلها واحسبها من drugs.base_price).

4. الأخطاء والاستجابات
Custom Exceptions فقط من app/utils/exceptions.py (NotFoundError, ConflictError, BusinessRuleViolation) تُرفَع من service.py. لا تستخدم HTTPException مباشرة داخل service — التحويل لكود HTTP يحدث في Global Exception Handler وحده.
أكواد الحالة: 201 (إنشاء)، 204 (حذف بدون محتوى)، 404، 409 (تعارض/تكرار)، 422 (خرق قاعدة عمل)، 401 (غير مُصادَق).
أي قائمة نتائج (List Endpoint) تدعم Pagination بنفس الصيغة الثابتة: {"items": [...], "total": N, "page": N, "limit": N} — لا تُرجَع قائمة خام أبدًا.

5. سلوكيات حساسة موثّقة مسبقًا (لا تُعاد مناقشتها)
حذف أي كيان مرتبط ببيانات تاريخية (دواء له طلبات سابقة مثلًا) → يُرفَض بـ BusinessRuleViolation، وليس Soft Delete تلقائي (لا تضِف حقل is_active من نفسك — لو احتجته فعلاً، دوّنه كسؤال مفتوح أولاً).
أي انتقال حالة حسّاس (زي إلغاء طلب مكتمل) يُسجَّل في audit_logs فورًا ضمن نفس الـ transaction.
التذكيرات لكل عميل تُجمَّع في رد واحد (Grouped by customer_id)، وليس صفًا منفصلًا لكل دواء — لتفادي إرسال رسائل متعددة منفصلة لنفس العميل في نفس الوقت.
فلترة "تم إرسال تذكير خلال 24 ساعة" تعمل على مستوى الاستعلام (SQL) قبل أي تجميع في بايثون.
زوج (drug_id_a, drug_id_b) في جداول التعارض/التوافق يُرتَّب تلقائيًا في الكود (الأصغر = a) قبل الإدخال، ولا يُترَك للـ Frontend يحدد الترتيب.

6. الاختبار والتقارير
أي Domain جديد يُختبَر حيًا على قاعدة بيانات Supabase الحقيقية (وليس Mock فقط) قبل اعتباره مكتملًا، عبر سكريبت اختبار أو httpx.AsyncClient.
كل تقرير نهائي يتضمن: (1) ملخص ما تم تنفيذه، (2) نتيجة اختبار حي بأرقام/نتائج فعلية، (3) قسم "أسئلة مفتوحة" لأي قرار خارج نطاق هذا المستند.
