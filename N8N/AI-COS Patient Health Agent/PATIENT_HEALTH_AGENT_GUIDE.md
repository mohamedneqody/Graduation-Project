## 1. نظرة عامة والهدف السريري والتجاري للمنظومة

في الصيدليات الإلكترونية الحديثة، لا يكفي فقط عرض قائمة بالأدوية والأسعار، بل يحتاج المريض (خصوصاً أصحاب الأمراض المزمنة) إلى **رعاية صحية استباقية (Proactive Clinical Guidance)** تضمن:
1. **فحص التفاعلات الدوائية (Drug Interactions):** التأكد من أن الأدوية السابقة والجديدة متوافقة سريرياً ولا تسبب مضاعفات خطيرة.
2. **التنبؤ الذكي بموعد إعادة الصرف (Smart Refill Alerts):** حساب موعد نفاد عبوة الدواء تلقائياً بناءً على نمط استهلاك المريض.
3. **توجيهات صحية مخصصة (Personalized Advice):** إعطاء نصائح طبية مرتبطة بحالته المزمنة (مثل مرضى الحساسية أو الضغط).
4. **ربط الصيدلي بحالة المريض (Human-in-the-Loop):** إشعار الصيدلي فوراً على تليجرام بأي حالة تحتاج متابعة.

يقوم **`AI-COS Patient Health Agent`** بتنفيذ كل هذه المهام في أقل من ثانيتين وبسرية بيانات طبية مطلقة.

## 2. المرحلة الأولى: معالجة البيانات وتجهيزها قبل وصولها للسير

لا يتم إرسال بيانات عشوائية من المتصفح إلى سير العمل، بل يمر كود الفرونت إند في ملف [`profile/page.tsx`](file:///D:/Graduation%20Project/AI-COS-Pharmacy/frontend/src/app/(storefront)/profile/page.tsx) بعدة مراحل معالجة وتحقق مسبقة:

```
[1. المريض يفتح البروفايل] ──▶ [2. التحقق من JWT Token] ──▶ [3. جلب الـ Profile من الباك إند] ──▶ [4. الحساب الرياضي للأيام] ──▶ [5. تجميع Payload]
```

### 🔹 2.1 التحقق من الهوية والأمان (Authentication Verification):
* بمجرد تحميل الصفحة، يستدعي الكود:
  ```typescript
  const supabase = createClient();
  const { data: { session } } = await supabase.auth.getSession();
  ```
* إذا لم تكن هناك جلسة مسجلة، يتم توجيه المستخدم فوراً لصفحة تسجيل الدخول (`/login`) لحماية خصوصية البيانات الطبية.

### 🔹 2.2 سحب بيانات المريض الحقيقية (Profile Fetching):
* يستدعي المتصفح نقطة الباك إند: `GET /api/v1/customers/me`.
* يعود السيرفر ببيانات المريض الرسمية:
  * `customer_id`: المعرف الفريد للمريض (UUID).
  * `full_name`: الاسم الحقيقي للمريض ("محمد ياسر").
  * `created_at`: تاريخ إنشاء الحساب ("2026-08-08").

### 🔹 2.3 المعالجة الرياضية للتواريخ (Tenure Calculation):
* يقوم الكود بحساب عدد الأيام التي قضاها المريض كعضو في الصيدلية رياضياً:
  ```typescript
  const daysSinceJoin = Math.floor(
    (Date.now() - new Date(customer.created_at).getTime()) / (1000 * 60 * 60 * 24)
  );
  ```

### 🔹 2.4 تجميع كائن البيانات (Payload Packaging):
* يتم دمج هذه البيانات مع الحالة المزمنة المحددة وتجهيز كائن JSON نظيف للإرسال:
  ```json
  {
    "customer_id": "ed680fa0-e241-4231-bae6-b377f96f03a6",
    "customer_name": "محمد ياسر",
    "order_count": 3,
    "chronic_condition": "حساسية ومناعة (Allergy)",
    "days_since_join": 25
  }
  ```

## 3. المرحلة الثانية: رحلة البيانات ونقطة الدخول (Webhook Ingestion & Transport)

لضمان عدم حدوث مشاكل **CORS** أو أخطاء الشبكة، يتم نقل البيانات عبر نفق بروكسي داخلي مُعدّ في `next.config.ts`:

1. **الطلب من المتصفح:** يُرسل الطلب إلى المسار النسبي:
   `POST /n8n-webhook/aicos-patient-health`
2. **إعادة التوجيه (Next.js Rewrite Proxy):** يقوم سيرفر Next.js بتحويل الطلب داخلياً إلى:
   `POST http://127.0.0.1:5678/webhook/aicos-patient-health`
3. **الاستقبال في n8n:** تستقبل العقدة الأولى (`Webhook`) الطلب وتخزن البيانات في متغير الـ JSON الداخلي:
   `$('Webhook').first().json.body`

## 4. المرحلة الثالثة: التشريح الهندسي لسير عمل n8n عقدة بعقدة

يتكون السير من **8 عقد مترابطة بدقة فائقة**:

```
[1. Webhook] ──▶ [2. Get Orders] ──▶ [3. Get Cycles] ──▶ [4. Build Prompt]
                                                              │
[8. Respond] ◀── [7. Notify Admin] ◀── [6. Parse Response] ◀── [5. Ask Ollama]
```

### 🔹 1. عقدة `Webhook`:
* **الوظيفة:** نقطة الدخول واستقبال الـ JSON القادم من واجهة المتصفح.

### 🔹 2. عقدة `Get Patient Orders` (استعلام المشتريات):
* **النوع:** Postgres Query Node.
* **الوظيفة:** تتصل مباشرة بقاعدة بيانات Supabase وتسترجع آخر 5 طلبات حقيقية للمريض مع أسماء الأدوية المشتراة وإجمالي الفاتورة.
* **ميزة الأمان:** مزودة بـ `alwaysOutputData: true` حتى لا يتوقف السير لو كان المريض جديداً ولا يملك طلبات سابقة.

### 🔹 3. عقدة `Get Churn Data` (استعلام دورات الاستهلاك):
* **النوع:** Postgres Query Node.
* **الوظيفة:** تستعلم من جدول `customer_cycles` عن متوسط عدد الأيام التي يستهلك فيها المريض عبوة الدواء (`avg_cycle_days`) وتاريخ آخر عملية شراء.

### 🔹 4. عقدة `Build Health Prompt` (المحرك الحسابي وهندسة الأوامر):
* **النوع:** JavaScript Code Node.
* **الوظيفة:**
  1. تحسب موعد نفاد العبوة:
     $$\text{Days Left} = \text{Last Purchase Date} + \text{Avg Cycle Days} - \text{Current Date}$$
  2. تحدد تنبيه إعادة الصرف: إذا كان متبقياً $\le 14$ يوماً تصدر تنبيهاً بقرب الموعد.
  3. تصيغ برومبت سريري منظم ودقيق يسأل الذكاء الاصطناعي بالإنجليزية ويطلب الرد بثلاثة أسطر محددة.

### 🔹 5. عقدة `Ask Ollama` (العقل التحليلي السريري):
* **النوع:** HTTP Request Node.
* **الرابط:** `http://host.docker.internal:11434/api/generate`
* **المودل:** `AI-COS-LFM-Q4:latest` (نموذج لغوي محلي فائق السرعة والأمان).
* **الوظيفة:** يحلل التفاعلات الدوائية والتوصيات الطبية محلياً بدون إرسال البيانات الطبية لأي خوادم خارجية حفاظاً على سرية المريض (HIPAA / GDPR).

### 🔹 6. عقدة `Parse Health Response` (استخراج وتبويب التوصيات):
* **النوع:** JavaScript Code Node.
* **الوظيفة:** تفكيك نص الذكاء الاصطناعي بواسطة Regular Expressions واستخراج:
  * `interaction_check`: نتيجة فحص التفاعلات.
  * `refill_alert`: تنبيه إعادة الصرف.
  * `ai_recommendation`: التوجيه الطبي المخصص.

### 🔹 7. عقدة `Notify Admin` (إشعار تليجرام للإدارة):
* **النوع:** Telegram API Node.
* **الوظيفة:** ترسل إشعاراً فورياً منسقاً بـ HTML لبوت تليجرام الصيدلية يحتوي على اسم المريض، مُعرّفه البرمجي (`Customer ID`)، ملخص الطلبات، والتوصية الطبية.

### 🔹 8. عقدة `Respond` (الرد على المتصفح):
* **النوع:** Respond to Webhook Node.
* **الوظيفة:** تعيد كائن الـ JSON النهائي للمتصفح ليتم عرضه داخل البطاقة البنفسجية في صفحة البروفايل فوراً وبدون أي تأخير.

## 5. المرحلة الرابعة: دور نموذج الذكاء الاصطناعي المحلي (Local LLM)

### 🧠 هندسة البرومبت الطبي (Clinical Prompt Architecture):
يتم إرسال السؤال للمودل في هذا القالب الاحترافي:
```text
You are a professional pharmacy clinical AI.
Patient: محمد ياسر
Condition: حساسية ومناعة (Allergy)
Total orders: 3
Recent drugs: Amaryl 2mg, alerid 10 mg 30 f.c.tabs, allergyl 4 mg 20 tabs
Chronic drugs: alerid 10 mg 30 f.c.tabs, allergyl 4 mg 20 tabs

Provide a short clinical health evaluation in EXACTLY 3 lines:
INTERACTION_CHECK: [one concise Arabic sentence verifying medication safety and absence of conflicts]
REFILL_ALERT: [one concise Arabic sentence about refill timing]
AI_RECOMMENDATION: [one actionable Arabic clinical tip for this patient]
```

### 🎯 النتيجة المرجعة:
1. **فحص التفاعلات:** *"لا توجد تعارضات معروفة بين أدوية الحساسية الحالية للمريض."*
2. **تنبيه التجديد:** *"يُرجى استشارة الصيدلي قبل إعادة التعبئة لتقييم استقرار الحساسية."*
3. **التوصية:** *"يُنصح بالحفاظ على انتظام الجرعات وتجنب المضادات الحيوية واسعة الطيف بدون استشارة الطبيب."*

## 7. أهم نقاط القوة لمناقشة مشروع التخرج (Graduation Defense Value)

عند مناقشة هذا الوكيل في مشروع التخرج، ركّز على **المعايير الهندسية الأربعة**:

1. **معمارية الـ Agentic RAG الحقيقية:**
   * النظام لا يعتمد على تخمين الـ AI، بل يسترجع بيانات المريض التاريخية من قاعدة بيانات SQL أولاً (Retrieval)، ثم يغذيها للنموذج اللغوي (Augmentation)، ثم يولد التقييم (Generation).
2. **الخصوصية والأمان الطبي (Data Privacy & Compliance):**
   * استخدام نموذج محلي داخل Ollama يعني أن بيانات المرضى وأدويتهم لا تخرج إلى خوادم خارجية مثل OpenAI، وهو متطلب أساسي في المعايير الطبية (HIPAA).
3. **صمامات الأمان وعدم التعطل (Fault Tolerance):**
   * وجود `alwaysOutputData` و `continueRegularOutput` يضمن أن النظام لن يتعطل حتى لو كان المريض مسجلاً لأول مرة أو لا يملك تاريخاً كافياً.
4. **التكامل ثنائي الاتجاه (Bi-Directional Communication):**
   * النظام يخدم المريض في واجهة المتصفح لحظياً، وفي نفس اللحظة يُرسل إشعاراً للصيدلي على هاتفه عبر تليجرام.
